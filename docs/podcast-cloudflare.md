# Publicación de podcasts: R2, Worker y Pages

## Arquitectura

`content/*/*/*/podcast/script.md` es la fuente editorial. `scripts/podcast.py` valida el guion y `scripts/tts.py` sigue siendo el motor Piper/FFmpeg. `scripts/podcast_publish.py` calcula la huella y coordina `scripts/storage/`: `local.py` para desarrollo y `r2.py` para el bucket privado `martina-edu-podcasts`. `infrastructure/cloudflare/src/index.ts` sirve únicamente MP3 inmutables por GET/HEAD mediante un binding R2, sin claves S3 ni escritura. `wrangler.jsonc`, `package-lock.json` y `bootstrap.mjs` permiten reconstruir la infraestructura. `.github/workflows/pages.yml` ejecuta el mismo Python que se usa localmente, verifica las URLs del Worker y solo entonces construye Pages.

Los objetos se guardan como `podcasts/<asignatura>/<curso>/<tema>/<sha256>.mp3` y `.json`. El MP3 y JSON se crean con `If-None-Match: *`, nunca se actualizan. El JSON contiene el hash de generación, checksum independiente del MP3, tamaño, duración, fecha, voz, checksums de modelo/configuración, versiones y capítulos. La fecha y el checksum del MP3 no forman parte del hash de generación.

La huella es SHA-256 de UTF-8 JSON con claves ordenadas, separadores compactos, sin NaN y sin espacios. Incluye, en orden, el texto efectivamente narrado *tras* sustituciones, las pausas, la identidad y los checksums del modelo, la versión de Piper, los parámetros Piper y FFmpeg que determinan el sonido y una versión explícita del pipeline. Los títulos y límites de capítulos no se narran en el motor actual, por lo que no cambian la huella. También omite rutas, marcas de tiempo, secretos, ID de CI y ajustes como `sample_seconds` que no afectan al episodio completo. El binario FFmpeg del runner tampoco entra en la huella: una actualización del sistema sin cambios en la receta no regenera podcasts. Si cambia el resultado audible del proceso, incrementa `PIPELINE_VERSION` en `scripts/podcast_publish.py`. Los checksums fijados para cada voz en `config/subjects.yml` identifican el modelo aunque el runner lo haya perdido; no son el checksum del MP3. Solo se descarga y verifica el modelo cuando falta el audio en R2.

`default` y `on_demand` permiten sintetizar guiones que ya existen. `disabled` excluye el tema. Actions nunca crea guiones mediante IA. No hay mecanismo editorial de aprobación de audio en este repositorio: una versión técnicamente validada se publica automáticamente. La página de podcast ofrece un enlace de descarga; todavía no hay reproductor completo.

## Configuración manual única

1. Crear o elegir una cuenta Cloudflare. En **Storage & databases → R2 → Overview**, completar la suscripción inicial de R2. Cloudflare exige este paso en la cuenta antes de poder emitir credenciales R2; el workflow no puede aceptarlo en nombre del propietario. [R2 Get started](https://developers.cloudflare.com/r2/get-started/).
2. En **Workers & Pages**, preparar o comprobar el subdominio de cuenta `workers.dev` y anotar su nombre. El Worker se llamará `martina-edu-audio`; su URL será `https://martina-edu-audio.<subdominio>.workers.dev`. No configurar dominio propio ni `r2.dev`. [workers.dev](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/).
3. Crear un token Cloudflare **bootstrap** limitado a esta cuenta con **Workers product Admin** (necesario para crear un Worker inexistente) y **Workers R2 Storage Write** (crear/consultar bucket). Crear un token cotidiano con **Editor** del Worker existente para despliegues posteriores. En una cuenta vacía el bootstrap crea el Worker; en las demás ejecuciones Wrangler usa el token cotidiano. [Roles de Workers](https://developers.cloudflare.com/workers/authorization/workers/), [API R2 bucket](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/methods/create/).
4. Crear credenciales S3 R2 **Object Read & Write**, sin permisos de administración de buckets. Para reconstruir una cuenta sin bucket y sin otra intervención, el token debe admitir objetos del bucket cuando Actions lo cree; en el panel se consigue aplicándolo a **todos los buckets** de esta cuenta. Es más amplio que limitarlo a un bucket ya existente, pero no permite crear ni borrar buckets. Si renuncias a reconstrucción automática desde cero y ya existe el bucket, puedes restringirlo solo a `martina-edu-podcasts`. El Worker lee con binding, no con dichas claves. [Tokens R2](https://developers.cloudflare.com/r2/api/tokens/).
5. En GitHub, **Settings → Secrets and variables → Actions**, añadir los secretos de la tabla siguiente y la variable `MARTINA_AUDIO_BASE_URL` con la URL exacta, sin barra final. En **Settings → Pages**, seleccionar **GitHub Actions** como fuente. Después ejecutar **Validar i publicar** desde Actions o enviar un commit a `main`. [Publicar Pages con Actions](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

| Nombre | Tipo | Uso |
| --- | --- | --- |
| `CLOUDFLARE_ACCOUNT_ID` | Secret | Cuenta de R2 y Wrangler |
| `CLOUDFLARE_BOOTSTRAP_API_TOKEN` | Secret | Consultar/crear bucket y crear Worker si falta |
| `CLOUDFLARE_API_TOKEN` | Secret | Actualizar Worker existente |
| `R2_ACCESS_KEY_ID` | Secret | Leer/escribir objetos S3 del bucket |
| `R2_SECRET_ACCESS_KEY` | Secret | Pareja de la clave S3 |
| `MARTINA_AUDIO_BASE_URL` | Variable | URL pública `workers.dev` del Worker |

No pegar claves en el repositorio, logs ni chats. El workflow se activa solo en `push` a `main` y `workflow_dispatch`; no expone secretos a PR externos. El nombre del bucket y el binding están versionados en `wrangler.jsonc`. Si se cambia el nombre, actualizar también `R2_BUCKET_NAME` del workflow. El origen CORS de Pages está en `wrangler.jsonc` como `SITE_ORIGIN`.

## Ejecución y recuperación

`npm ci && npm test && npm run typecheck && npx wrangler deploy --dry-run` dentro de `infrastructure/cloudflare/` verifica el Worker sin cuenta. `python -m unittest discover -s tests` prueba los backends sin Cloudflare. Para probar el almacén local: `python scripts/build.py tts sync <tema> --backend local`; sigue usando el modelo y FFmpeg instalados. `tts check`, `inspect`, `verify`, `publish` y `sync` admiten `--backend r2` o `--backend local`. Para R2, exportar las mismas variables de cuenta, clave, secreto y URL base desde un gestor seguro. `tts sync --all --download-models` crea `audio/published.json`, que queda fuera de Git y de Pages.

Ante un par MP3/JSON incompleto, checksum distinto, 403 o fallo de red, la publicación se detiene. **No borrar ni sobrescribir el objeto**: inspeccionar ambos objetos y el log; recuperar el JSON solo tras verificar los bytes del MP3, su checksum y la huella original, o generar una nueva versión tras cambiar un factor real de audio. La ejecución fallida no despliega Pages, por lo que conserva la referencia publicada anterior. Las versiones antiguas siguen en R2; para volver a una versión previa se puede usar su URL inmutable tras verificar el objeto y volver a publicar una página que la referencie. El código no hace limpieza automática.

La concurrencia de Actions usa un único grupo serializado y `cancel-in-progress: false`. Antes de sintetizar se consulta R2 dos veces y antes de subir se comprueba de nuevo; `If-None-Match: *` evita sobrescrituras entre procesos. Fuera de Actions dos runners pueden sintetizar en paralelo la misma versión; uno fallará al crear el objeto y requerirá reconsultar. No hay bloqueo distribuido. El sistema conserva objetos incompletos para análisis en vez de borrarlos automáticamente.

## Reconstrucción y diagnóstico

El bootstrap hace GET del bucket; solo un 404 permite POST de creación **Standard**. Comprueba que ni `r2.dev` ni un dominio personalizado dan acceso público al bucket; si un bucket preexistente está expuesto, falla hasta corregirlo en Cloudflare. Consulta si existe el Worker, selecciona el token adecuado, ejecuta `wrangler deploy` con su binding versionado y comprueba `/health`. Después la CLI valida R2, reutiliza o crea cada MP3, verifica la lectura S3 y el HEAD público, escribe el manifiesto, construye la web/PDF y despliega Pages. Repetir el workflow reutiliza bucket, Worker y MP3. Nunca llama a borrar bucket u objetos. Los tests simulan cuenta vacía, recursos existentes y 403; **no equivalen a una reconstrucción real**. Para validarla en una cuenta de prueba aislada, configura sus secretos, ejecuta el workflow dos veces y comprueba que la primera crea recursos y la segunda los reutiliza; no elimines recursos de producción.

Un 403 indica permisos, no ausencia. Un 404 del Worker con R2 correcto sugiere binding/ruta errónea; `/health` solo prueba despliegue, mientras la CLI prueba cada URL de MP3 antes de Pages. Un checksum distinto o par incompleto exige investigación manual. Si una actualización real de FFmpeg altera el sonido o la codificación que debe publicarse, incrementa `PIPELINE_VERSION` deliberadamente antes de generar una nueva versión; las actualizaciones del runner por sí solas no invalidan audios aprobados.

## Coste y límites vigentes (octubre de 2026)

R2 Standard incluye 10 GB-mes, 1 millón de operaciones Clase A y 10 millones Clase B al mes. Después cuesta 0,015 USD/GB-mes, 4,50 USD/millón A y 0,36 USD/millón B; la salida de R2 es gratuita. Cada HEAD/GET de verificación y cada reproducción cuentan como lecturas. No se usa Infrequent Access. [Precios R2](https://developers.cloudflare.com/r2/pricing/). Workers Free permite 100.000 solicitudes diarias; al superar el límite, las solicitudes pueden fallar. [Límites Workers](https://developers.cloudflare.com/workers/platform/limits/). GitHub indica que los runners estándar son gratuitos para repositorios públicos, pero la síntesis CPU puede alargar los jobs y alcanzar límites de duración o concurrencia. [Facturación de Actions](https://docs.github.com/en/actions/concepts/billing-and-usage). Conviene revisar el consumo en los paneles de Cloudflare y GitHub tras la primera publicación; no hay monitorización automática en esta fase.
